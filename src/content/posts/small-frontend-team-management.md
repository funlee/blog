技术做得不错，开始带一个小团队，似乎是很自然的职业发展。但真正接过管理职责后，工作可能会变成另一种模样：代码写到一半有人来问问题，刚处理完需求变更，又要参与面试；团队人数增加了，交付却未必更顺畅，自己反而成了最忙的人。

这时很容易产生一种焦虑：同事都在学习技术、完成项目，自己却被各种琐事占据，技术成长和工作产出都变少了。

志遥在「前端早早聊」关于小型前端团队管理的分享中，回顾了类似的转变。他把这些经历整理成个人转变、团队建设、团队协作三个方面，共十五个问题。本文根据[当时保存的分享笔记](https://www.yuque.com/funlee/eceni8/ka60wu)重新梳理。涉及丁香医生团队的经历均来自分享者，文末的实践建议是基于笔记的整理与延伸。

这份分享最值得反复琢磨的一点是：**当一个人开始对团队负责，除了完成自己的工作，还要让其他人能够更顺畅地完成工作，并在这个过程中获得成长。**

## 一、先看业务阶段，再谈管理方法

理解这些经验，需要先交代它们发生的环境。按照分享中的回顾，志遥于 2016 年加入丁香园，2017 年夏天开始正式负责丁香医生的前端团队。当时在线问诊业务仍在探索，产品形态、业务方向和团队规模都在变化。

这段发展过程，可以从文字记录中归纳为四个阶段：

| 阶段 | 业务与团队的变化 | 逐渐暴露的问题 |
| --- | --- | --- |
| 2016—2017 年探索期 | 先通过 Web 验证业务，再决定用 App 承载 | 上线速度优先，代码质量与后续维护之间出现张力 |
| 2017 年扩张期 | App 快速迭代，前端团队扩充 | 规范不足、成员能力差异、人才梯度不完整 |
| 2018 年多方向探索期 | 原有业务增长，同时尝试新的健康业务 | 发布节奏频繁变化，项目管理压力和技术焦虑增加 |
| 2019 年相对稳定期 | 业务模型逐步清晰，团队进入相对稳定的发展状态 | 更系统地改善研发效能、技术沉淀和业务分工 |

同一个团队，在不同阶段遇到的问题并不一样。两三个人时靠默契就能完成的协作，扩展到七个人后，可能需要明确的规则；业务尚未验证时，快速试错很重要，业务趋于稳定后，长期维护成本会越来越难忽略。

因此，管理方法要放回具体场景里判断。先弄清当前最需要解决的问题，再决定采用什么制度、工具或分工方式，才能避免为了“像一个成熟团队”而堆叠流程。

## 二、角色转变：从自己冲在前面，到帮助团队向前

### 1. 反复亲自补位，容易让负责人变成瓶颈

分享中有一个很典型的变化：团队从两个人发展到三个人时，负责人还能享受写业务、学技术、快速交付的状态；当团队从三个人扩展到七个人，各种协调工作开始不断打断个人开发。

志遥最初选择的办法，是在其他人下班后继续补上自己想做的业务。但坚持一段时间后，个人和团队的交付质量、效率都没有明显改善。

随后，他尝试把任务分出去，再跟踪进度。这比全部自己承担好一些，却仍然没有解决问题：新人不熟悉团队，交流不够坦诚，能力和代码风格存在差异。任务虽然分出去了，完成任务所需的条件并没有全部建立起来。

后来的调整更接近管理工作的核心：让成员主动认领任务，由负责人协调不合理的分工；建立代码规范并配合工具执行；通过 Code Review 促进交流；在业务相对清晰后，用虚拟小组承接不同业务。

这些做法共同解决的是团队如何持续运转的问题。负责人仍然需要技术判断力，也可能参与关键实现，但不必通过包揽最难的任务来证明自己的价值。更有意义的变化是：过去必须由自己完成的事情，逐渐有其他人能够独立承担。

### 2. 情绪稳定，会影响问题能否被及时看见

业务方向反复、成员成长不及预期、合作不顺畅、骨干离开，都可能让负责人产生焦虑。原分享用“心如止水”提醒自己，避免把未经处理的负面情绪不断传递给团队。

这条提醒可以理解为：在表达判断和提出要求之前，先分清事实、感受与行动。需求调整是事实，对返工感到失落是感受，重新确认优先级和交付范围则是下一步行动。

如果每次暴露问题都会迎来指责，成员就可能倾向于晚一点说、少说一点，甚至等到实在兜不住才求助。负责人得到的信息反而更少，焦虑也更难消除。

稳定的沟通不要求一个人永远没有情绪。它要求我们能够把情绪带来的冲动，与需要团队共同处理的问题区分开，让成员知道：问题可以被讨论，困难可以被提前提出。

### 3. 信息管理和全局思考，也是技术负责人的工作

负责人通常比成员更早知道业务调整的原因。如果只传递“这个需求不做了”，没有解释背景，成员看到的就可能是：上周的努力，这周突然失去了意义。

另一个例子是技术方案。团队花了一周解决某个难题，最后才发现其他部门已经有成熟实践。问题未必在于研发能力，而在于有价值的信息没有被及时获取和连接起来。

原分享因此强调，负责人需要主动寻找信息，并做适当的筛选与传递。这也要求视角向外扩展：业务为什么做这个决定？其他团队有哪些限制？当前技术投入究竟在解决什么问题？

信息传递的目标，是帮助成员理解与自身工作有关的背景，并获得做判断所需的条件。未经确认的消息、与任务无关的细节，以及不适合公开的内容，都不应机械地转发。

### 4. 保持技术深度，也给健康留下位置

开始带团队以后，技术成长的方式需要重新安排。原分享最后仍然强调深耕技术，并提到志遥在 2019 年用 TypeScript 实现了小程序的 [Sentry SDK：sentry-miniapp](https://github.com/lizhiyao/sentry-miniapp)，把学习落实到具体作品中。

这与角色转变并不矛盾。负责人可以减少无差别地接手业务细节，把有限的技术时间放在关键问题、架构判断和有持续价值的实践上。

与此同时，健康不能长期排在交付和学习之后。分享者也回顾了自己对健康的忽视，以及后来做出的调整。对小团队而言，如果负责人长期靠透支自己维持运转，这种工作方式本身就需要被重新审视。

## 三、交付管理：既要把事情做完，也要理解为什么做

### 1. 发布节奏需要共同磨合

原分享中，发布周期经历了多次调整：早期 H5 随做随发，App 按需求量排期；随后尝试两周、一周发版，业务压力大时，甚至出现过一天内发布多个小程序版本的情况。

频繁发布让技术团队疲惫，单方面拉长周期又让业务方不满意。经过反复协调，到 2019 年，团队逐渐形成每周一个主版本、必要时支持额外版本的节奏。

这个案例的重点在于磨合过程。每周发一次是当时团队找到的平衡，并不能直接作为所有团队的标准。发布频率需要同时考虑业务时效、需求规模、验证成本、依赖关系和质量保障能力。

只讨论“快一点”或“慢一点”，容易陷入双方立场的拉扯。进一步讨论哪些需求必须赶当前窗口、哪些可以进入下一批、增加一次发布需要付出什么成本，才更容易形成共同的判断。

### 2. 遇到问题，检查机制能否提供支持

分享者回顾，自己曾把不少问题归结为个人能力：出了 Bug 是研发不够认真，需求变化是产品没想清楚，团队不顺畅则是自己不适合管理。

这样的解释可能包含部分事实，却很难指导团队持续改善。更进一步的问题是：流程有没有帮助人把事情做好？

例如，交付质量不稳定，可以检查自测、提测的要求是否清楚，关键路径有没有回归验证；需求经常临时改变，可以回看变更如何进入迭代、影响是否被重新评估。原分享提到的规范与自动化测试，都是在为人的能力和注意力提供补充。

这并不意味着个人不需要承担责任。责任要落实，机制也要改进，否则相似的问题很容易换一个人、换一个项目再次出现。

### 3. 技术价值可以逐层积累

“过去一年，你对业务的贡献是什么？”这是原分享中促使志遥重新思考技术价值的一个问题。

完成了多少需求，可以描述工作量，却不足以完整说明技术团队的贡献。他把技术持续交付的价值进一步分成四层：

| 价值层次 | 关注的问题 | 可以观察的结果 |
| --- | --- | --- |
| 基本交付 | 能否实现需求并上线 | 需要的功能被完成 |
| 技术增值 | 能否提高质量和效率 | 同类工作更可靠，重复劳动减少 |
| 软件资产 | 能否持续、顺畅地交付 | 工具、组件、流程和工程能力得到积累 |
| 技术附加值 | 能否理解并推动有效的业务价值 | 技术判断参与到问题定义和方案选择中 |

这是分享者理解技术价值的一种框架。它可以帮助我们检查投入的方向，但不必把它变成僵硬的等级，也不意味着某类职能对某一层价值拥有绝对边界。

对小团队来说，一个实际的启发是：评估技术建设时，需要同时说明它解决什么问题，以及收益如何体现。组件库、持续集成、架构升级都有潜在价值，但维护成本也真实存在。

同样，面对“紧急需求”，可以先把业务理由问清楚：它解决什么用户问题？时间限制来自哪里？延后会产生什么影响？这些问题有助于双方确认优先级，也能避免把所有需求都按最高优先级处理。

## 四、人才建设：招聘、培养与离开，需要连起来看

### 1. 招聘前先明确缺口

志遥在分享中提到，2019 年曾持续招聘资深前端工程师，投入了不少精力，却迟迟没有合适结果。后来的反思集中在三个环节：招聘前想清楚、面试中判断准确、面试后稳妥决策。

招聘前需要明确业务处境、现有人才结构、岗位职责和招聘优先级。团队究竟缺独立承担复杂项目的人，还是缺能改善工程体系的人？如果缺口不清楚，招聘标准就容易变成一长串技术名词。

面试时，除了专业能力，还要了解候选人愿意承担什么工作，以及双方的协作方式是否匹配。这里的匹配应落到具体的工作要求和沟通行为，避免仅凭“聊得来”判断。

最终的选择，也需要同时考虑能力、工作意愿和团队期待。把人招进来只是起点，双方能否在实际工作中兑现彼此的预期，才是招聘结果的重要部分。

### 2. 培养成员，要与任务和目标相连

原笔记关于人才培养的直接提醒很简短：负责人要对成员的发展负责。把这句话放回日常工作，意味着分配任务时除了考虑谁做得最快，还要考虑这项任务能帮助谁建立什么能力，以及需要提供什么支持。

培养可以发生在一次方案讨论、一次 Review、一次上线后的复盘中。关键在于，让成员逐渐理解判断依据，而不只是接收一个最终答案。

目标管理则决定这些努力能否积累。分享者提到自己曾经设定远超团队能力的目标、同时推进过多方向，也曾出现季度之间目标大幅转向的问题。结果往往是团队疲惫，成果却没有形成连续性。

他通过学习和应用 OKR 改善这些问题。对读者而言，值得带走的是目标背后的要求：方向要明确，重点要集中，结果要能够检查，变化要有解释。仅仅把任务清单换成 O 和 KR，并不能自动解决目标过散的问题。

### 3. 反馈需要具体，也需要支持

原分享借用了“帮助与安慰”的比喻，强调负责人很难凭一次谈话就改变一个人，但可以持续提供帮助，理解成员的处境。

落实到工作反馈，可以沿着具体事实展开：发生了什么，对项目或协作产生了什么影响，期待怎样的变化，又能提供什么支持。这样的对话，比笼统地评价“能力不行”或“态度有问题”更容易让对方理解。

支持与明确要求可以同时存在。只有安慰，成员可能不知道需要改进什么；只有结论，成员又可能不知道怎样改进。日常把期待和困难谈清楚，也能减少集中绩效沟通时的突然与误解。

### 4. 面对离开，既要有判断，也要保留尊重

骨干离职会让负责人失落，面对长期不匹配的情况也可能犹豫。原分享提醒，不能仅因不舍或不忍，就一直回避已经显现的问题。

理解这条建议时，需要把“果断”放在充分沟通和判断之后。先确认职责、期待与实际困难，区分暂时受阻和长期不匹配，再决定下一步。确定离开后，把交接、责任承接和必要的信息说明做好，对双方都更负责。

团队与成员的关系，会随着业务和个人目标变化。接受这种变化，也是管理的一部分。

## 五、技术沉淀与团队氛围，决定成长能否持续

当业务进入相对稳定阶段，丁香医生前端团队投入了更多精力建设小程序研发体系、持续集成服务和小程序组件库。按照分享者的回顾，这些工作帮助团队改善交付，也让成员获得了技术成长。

这个案例把技术建设与业务工作连接了起来。日常需求里反复出现的问题，可以成为技术沉淀的起点；沉淀出的能力，又应回到实际项目中接受检验。

因此，判断技术沉淀是否有效，可以关注它有没有被使用、是否降低了重复成本、有没有明确的维护责任。一个规模不大但能持续帮助同事的工具，也可能比一个长期无人使用的平台更有价值。

团队氛围同样影响这些工作。原分享用快乐、优质、高效、成长、自由描述团队文化，并把快乐放在很重要的位置。

这些词需要通过日常行为体现：成员能否表达不同意见，遇到问题能否求助，技术讨论是否针对事实，个人是否有一定的选择空间。交付要求越清楚、合作越可信，成员也越容易在共同边界内获得自主性。

如果文化只停留在口号上，而实际奖励的是独自救火、隐瞒风险和无休止加班，团队最终会按实际发生的事情理解管理者的期待。

## 六、跨团队协作：承诺目标之前，先确认依赖

原分享最后一个案例是 App 热更新系统的替换。前端团队把用 A 系统替换 B 系统写进了自己的 KR，却没有提前与移动端充分沟通。移动端也有自己的目标与安排，最终这项工作延期落地。

这类问题很容易发生：从本团队看，目标合理、技术方案也明确；放到完整协作关系里，却还没有确认其他团队是否愿意投入、能否投入，以及什么时候投入。

负责人在制定目标时，需要同时看见外部依赖。涉及共同完成的事项，应先讨论收益、工作量、时序和风险，再形成双方能够承担的计划。只把自己的期限通知对方，往往还不足以建立协作。

原分享把这一点概括为共赢。它可以落到很具体的问题上：这件事对合作方有什么帮助？他们需要承担什么成本？哪些约束必须共同解决？能回答这些问题，目标才更接近可执行的共同承诺。

## 七、把笔记变成一次可以开始的改进

以下是根据这份分享延伸出的实践建议，并非丁香医生团队的原始执行清单。初次带团队时，可以先选择一个反复造成损耗的问题，做一个范围有限的改进。

| 如果经常遇到这种情况 | 可以先做的事情 | 之后观察什么 |
| --- | --- | --- |
| 负责人不断被打断、亲自补位 | 记录常见求助，区分知识缺口、职责不清和关键决策 | 同类问题是否逐渐能够由成员独立处理 |
| 需求变化带来返工和抱怨 | 变更时同步原因、影响及优先级调整 | 成员能否理解变化，受影响的承诺是否得到更新 |
| 发布前总是集中救火 | 回顾一次交付，补齐最薄弱的自测或提测要求 | 相似问题是否更早被发现 |
| 技术建设与业务脱节 | 为一项建设写清使用者、解决的问题和维护责任 | 是否有人持续使用，重复成本是否下降 |
| 跨团队目标经常延期 | 在确认期限前，把依赖和投入与合作方逐项对齐 | 双方是否对责任和时间形成一致预期 |

改进开始后，还需要留出复盘的机会。有效就继续完善，无效就回到问题本身重新判断。小团队的精力有限，能让一个高频问题少发生几次，通常就能为下一步改进腾出空间。

原分享中的十五个点，最终都回到了几件相互关联的事情：理解业务阶段，关注价值如何通过团队交付出来，帮助成员成长，也照顾彼此的健康与工作感受。

技术负责人不可能提前消除所有问题。但可以通过一次次更清楚的判断、更及时的沟通和更具体的支持，让团队遇到问题时有办法处理，让成长能够持续发生。
