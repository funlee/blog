《构建之法》让我把目光从“程序能否运行”，移向软件工作的全过程：需求是否值得做，团队如何协作，质量怎样验证，以及用户能不能顺利完成任务。

原笔记并不是逐章完整摘要，主要记录了概论、个人技术与流程、需求分析、项目管理和用户体验。这里沿着“为什么做—怎样做—如何确认做对”重新组织，并保留已有的需求分析配图。

## 程序、软件与产品，关注的范围逐步扩大

原记录用几组关系区分了算法、程序、软件工程和商业模式。它们可以当作理解层次的提示，而不必视为严格的数学等式。

算法与数据结构帮助实现功能，工程活动让代码能够被协作开发、验证和维护；当软件成为产品，还要回答谁需要它、怎样持续提供价值等问题。

这也解释了为什么“能跑”不是质量的终点。用户满意度、可靠性、可维护性，以及团队能否稳定地继续交付，都值得观察。

## 需求不只是用户说出口的一句话

原笔记强调，需求需要捕捉和分析。用户提出的往往是某种解决办法，团队还需要理解背后的场景与困难。

例如，“加一个导出按钮”描述的是功能。继续追问，可能会发现用户需要把数据交给另一个系统，或定期整理报告。只有了解后续用途，才知道应该输出什么格式、包含哪些内容，以及怎样处理错误。

这个例子是对笔记的延伸说明。它提醒我们，需求分析不是把请求原样抄进任务列表，而是减少对问题的误解。

### 从不同角度获取信息

| 方法 | 适合帮助理解什么 |
| --- | --- |
| 访谈与焦点讨论 | 用户的目标、语言和分歧 |
| 观察与日志研究 | 实际场景中发生了什么 |
| 问卷 | 在明确问题后收集更广泛的反馈 |
| 卡片分类 | 人们如何理解、组织和查找信息 |
| 对比实验 | 在可比较的条件下观察方案差异 |

功能之外，还要考虑性能、可靠性、开发过程和外部约束。使用者、购买者、监管方和开发团队可能关心不同的问题，不能只听见其中一方。

## 用 NABCD 把方案讲清楚

原笔记记录了 NABCD 框架。它帮助把一个想法从“我觉得不错”，整理成别人能够讨论的主张。

| 维度 | 需要说明的内容 |
| --- | --- |
| Need：需求 | 谁在什么场景下遇到了什么问题？ |
| Approach：做法 | 准备怎样解决，关键路径是什么？ |
| Benefit：收益 | 与原来的办法相比，改善在哪里？ |
| Competition：竞争 | 用户还有什么替代选择？ |
| Delivery：交付与推广 | 怎样让目标用户接触并使用它？ |

原记录曾把 D 同时写成 Delivery 和 Data。这里沿用其后“电梯演说”模板中的交付与推广含义；数据可以支持各项判断，不另当作一个未经说明的替换定义。

**延伸练习：** 尝试在一段话里说清这五点。如果“目标用户”只能写成“所有人”，“收益”只能写成“更加方便”，说明方案还需要进一步收窄。

## 资源有限，功能不能平均用力

原笔记记录了维持、抵消、优化、差异化和不做几种处理方式。它们提醒团队：并不是每项功能都值得做到最好，也不是竞争者拥有的功能都必须跟进。

| 处理方式 | 可以理解为 |
| --- | --- |
| 维持 | 以合理成本保持必要能力 |
| 抵消 | 弥补明显短板，达到足够可用 |
| 优化 | 对重要能力持续投入、改善质量 |
| 差异化 | 形成对目标用户真正有意义的区别 |
| 不做 | 明确舍弃，避免稀释资源 |

## 测试是持续获得反馈的方式

原笔记列出了单元测试的几个重要要求：速度快、结果可重复、相互独立，并与产品代码一起维护。这些要求让测试能够频繁执行，在修改时及时提供反馈。

覆盖率可以帮助发现未检查的路径，但不能单独证明程序正确。即使某段代码被执行过，断言也可能没有真正检验预期行为。

回归测试的价值，是在改变以后检查已有功能是否仍然符合预期。性能分析工具则回答另一个问题：资源和时间实际花在哪里。先测量，再优化，比仅凭直觉修改更有依据。

## 估时与风险：把愿望和判断分开

原笔记提醒要区分目标、估计和决心。希望某天交付，是目标；根据任务和经验判断需要多久，是估计；愿意投入多大努力，则是决心。三者有关，却不能相互代替。

还有两个原先混在一起的提醒，需要分开理解：

- **估时容易偏乐观：** 工作中的未知和依赖，往往比最初计划更复杂。
- **加人存在协调成本：** 对已经延期的项目，增加人员还可能带来培训、沟通与任务重新分配的负担，不能把人数直接换算成速度。

后一点通常与布鲁克斯定律相关，可参见这份[软件项目管理课程材料](https://chess.eecs.berkeley.edu/pubs/891/BrooksITProjectManagement16Feb12.pdf)。它不是原笔记中霍夫斯塔特提醒的另一个表述。

风险管理也应尽量前移：识别可能发生的问题，说明影响和触发信号，准备应对方式，而不是等问题出现后只靠临时救火。

## 用户体验：让正确操作更容易发生

原记录中的体验提醒很实用：及时反馈、保持一致、记住必要的选择、帮助用户识别错误，并提供合适的说明。

整理时需要纠正一个分类问题：这些属于一般的可用性考虑，不能全部归为“费茨法则”。费茨法则讨论的是指向目标的难度与距离、目标尺寸的关系，可参见[斯坦福大学的交互设计课程材料](https://hci.stanford.edu/courses/cs377e/2016/sp/lectures/10-interaction-design.pdf)。

对日常开发而言，可以在交付前亲自走一遍核心流程：第一次使用的人能看懂下一步吗？点击以后有反馈吗？操作失败后知道怎样继续吗？

## 一份交付前的简短检查

1. 我们是否说清楚了用户与场景，而不是试图服务所有人？
2. 核心功能是否产生了可以说明的价值？
3. 关键行为是否有验证，失败后是否能够定位原因？
4. 工期判断是否包含未知、依赖和协作成本？
5. 用户是否能够理解流程，并从错误中恢复？

软件工程的价值，正是在这些连接处显现：把代码、需求、协作和体验放进同一个持续改进的过程。
