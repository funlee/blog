滚动、输入和窗口缩放都可能在短时间内触发很多次事件。防抖（debounce）与节流（throttle）用不同的规则减少处理次数：防抖等待连续操作停下来，节流则控制持续操作期间的执行频率。

## 先用时间线区分

假设事件发生在第 0、100、200、700 毫秒，等待时间设置为 300 毫秒。在定时器没有额外延迟的理想情况下：

| 策略 | 执行时间 | 含义 |
| --- | --- | --- |
| 不处理 | 0、100、200、700 | 每次事件都执行 |
| 尾部防抖 | 500、1000 | 距离最后一次调用安静了 300ms 才执行 |
| 首次立即、保留末次的节流 | 0、300、700 | 首次立即执行，连续调用时保留最新一次参数等待间隔结束 |

真实定时器可能延后，因此这些时间用于理解规则，不是精确定时保证。节流与防抖还有其他选项组合，使用工具库时应明确 `leading`、`trailing` 等配置的语义。

## 防抖：等连续操作停下来

搜索输入通常不需要每输入一个字符就发送请求，可以等用户暂时停止输入后再处理。尾部防抖会在每次调用时重新计时，使用最后一次调用的参数与 `this`。

```javascript
function debounce(fn, wait) {
  let timer = null;

  function debounced(...args) {
    const context = this;
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      fn.apply(context, args);
    }, wait);
  }

  debounced.cancel = function () {
    clearTimeout(timer);
    timer = null;
  };

  return debounced;
}
```

参数应是有效的函数和非负等待时间；这里省略了参数校验。封装后的函数不返回未来执行的结果，也没有加入 `flush`、`maxWait` 等高级选项。

```javascript
// input 为页面中已经取得的输入框
const search = debounce(function (keyword) {
  console.log('搜索：', keyword);
}, 300);

function onInput(event) {
  search(event.currentTarget.value);
}

// input.addEventListener('input', onInput);
// 页面卸载或组件销毁时：
// input.removeEventListener('input', onInput);
// search.cancel();
```

在事件处理函数里先读取字符串，再把它传给防抖函数，可以避免延后读取事件对象时依赖已经变化的事件上下文。

尾部防抖的一个特点是：如果用户一直持续触发，函数就可能一直不执行。需要持续反馈的交互，往往更适合节流，或者使用支持最大等待时间的实现。

## 节流：持续操作时仍按间隔响应

滚动过程中更新位置、持续拖拽时提交进度等场景，通常既不希望执行过于频繁，也不希望必须等操作结束后才看到变化。

下面的版本约定：第一次立即执行；间隔内再次调用时，保留最新参数；间隔结束后补一次末次调用；没有额外调用就不会凭空补一次。

```javascript
function throttle(fn, wait) {
  let last = -Infinity;
  let timer = null;
  let pendingArgs;
  let pendingThis;

  function invoke() {
    const args = pendingArgs;
    const context = pendingThis;
    pendingArgs = pendingThis = undefined;
    timer = null;
    last = performance.now();
    fn.apply(context, args);
  }

  function throttled(...args) {
    pendingArgs = args;
    pendingThis = this;
    const remaining = wait - (performance.now() - last);

    if (remaining <= 0) {
      clearTimeout(timer);
      invoke();
    } else if (timer === null) {
      timer = setTimeout(invoke, remaining);
    }
  }

  throttled.cancel = function () {
    clearTimeout(timer);
    timer = null;
    pendingArgs = pendingThis = undefined;
    last = -Infinity;
  };

  return throttled;
}
```

这里使用单调时钟 `performance.now()` 计算经过时间，避免系统时间调整干扰间隔。执行前先清理待执行状态，即使业务函数抛出异常，也不会因为某个“正在执行”标志忘记恢复而永久失效。

同样，这只是面向普通回调的教学实现，不返回调用结果，也不等待异步函数完成。`cancel` 会取消尚未执行的末次调用并重置状态，下次调用可以立即执行。

## this 和参数为什么需要显式保存

定时器稍后才会运行，不能把定时器回调自己的调用上下文当成原始事件处理函数的上下文。应在包装函数调用时捕获 `this` 和参数，再通过 `fn.apply(context, args)` 传入。

`apply` 的两个参数分别是接收者和参数列表，`fn.apply(this.arguments)` 并不能表达“把 this 和所有参数原样传进去”。如果使用箭头函数作为业务回调，它的 `this` 则仍由词法作用域决定，包装器不能重新绑定。

## 控制频率不等于解决全部异步问题

防抖可以减少搜索请求，但不能阻止先发出的请求更晚返回。避免旧结果覆盖新结果，还需要请求序号、取消请求或其他竞态处理机制。

节流只控制发起调用的时间间隔，不限制同时进行中的异步任务数量。如果一次请求持续很久，下一次节流调用仍可能发起新的请求。需要“前一次完成后才能开始下一次”时，应另行设计排队或互斥逻辑。

按钮防抖也不能替代服务端的幂等与重复提交校验。选择这些工具时，应明确它们解决的是事件频率，而不是所有业务一致性问题。
