理解 Fiber，可以先从一个用户能感知的问题出发：当组件树很大，一次更新占用主线程过久时，输入、滚动和动画都可能变得不流畅。Fiber 为 React 拆分、保存和调度渲染工作提供了基础。

本文讨论核心思想，不把某个版本的内部字段或调度算法当作稳定 API。原笔记写于 2021 年；文中提到的 React 18 并发特性，是为了补充后来如何使用这套基础设施。

## 为什么一次更新可能阻塞页面

React 更新页面，需要根据新的 props 和 state 计算组件输出，再判断哪些宿主节点需要改变。早期协调过程主要沿组件树同步递归执行，一旦开始，就很难在中途暂停并保存完整进度。

浏览器主线程还要处理输入、执行其他脚本和参与渲染。如果一段 JavaScript 持续运行很久，这些工作只能等待。

以 60Hz 屏幕为例，一帧约为 16.7ms，但这不是 JavaScript 独占的时间预算，浏览器也需要处理样式、布局和绘制。高刷新率屏幕的帧间隔还会更短。因此，不应把“每次计算低于 16ms”理解为绝对流畅的保证。

## Fiber：把隐含在调用栈里的进度显式保存

递归遍历时，“当前处理哪里、处理完以后返回哪里”等信息保存在调用栈中。Fiber 将组件相关的工作信息放进可管理的数据结构，让 React 能在合适的边界暂停，并在之后继续处理。

一个 Fiber 节点可以关联组件类型、props、state、更新信息和宿主实例等。常见的结构关系包括：

| 关系 | 用途 |
| --- | --- |
| `child` | 指向第一个子节点 |
| `sibling` | 指向相邻兄弟节点 |
| `return` | 指向父级方向的节点 |
| `alternate` | 关联当前树与工作中的对应节点 |

这些指针让遍历不必完全依赖函数递归，但 Fiber 仍然表示树状关系，不能简单理解成一条普通链表。具体字段和优先级表示方式会随着 React 版本演进。

## current 与 work-in-progress

可以把当前已经提交、用于显示界面的树理解为 current tree；React 在计算下一次更新时，会构建或复用 work-in-progress tree。

工作中的树并不意味着浏览器已经展示了半成品。React 可以先计算下一版结果，必要时暂停、重新开始或舍弃其中的工作，再在提交阶段把完成的结果应用到界面。

这种区分也是组件渲染必须保持纯粹的重要原因：如果渲染过程可能被重试或放弃，那么在渲染函数里发送请求、修改外部对象，就可能产生无法对应到最终界面的副作用。

## render 与 commit 不能混为一谈

一次更新可以从两个阶段理解：

- **render 阶段**：调用组件、协调子节点、计算需要进行的变化。在启用相应并发能力时，这部分工作可以被中断或重做。
- **commit 阶段**：把确定的变化应用到宿主环境，例如修改 DOM、处理 ref 和相关生命周期工作。DOM 提交过程不会为了时间切片而把半套变更留给用户。

Effect 也需要区分种类和时机，不能全部笼统归为“render 完立刻执行”。例如布局相关 Effect 与普通 Effect 的安排不同，普通 Effect 是否在绘制前执行还受交互等因素影响。理解 Fiber 时，先抓住“计算结果”和“应用结果”的边界更重要。

## 时间切片是一种协作式调度

下面是帮助理解的伪代码，不是 React 的源码，也不是可以直接粘贴使用的调度器：

```text
取得待处理的工作单元
只要还有工作，并且本轮不需要让出执行权：
    处理一个工作单元
    保存下一个工作位置
如果还有工作：
    安排后续继续处理
否则：
    提交已经完成的结果
```

“可中断”并不是系统可以在任意一条 JavaScript 指令处抢走控制权。React 需要在工作单元之间检查是否让出执行权；如果某个组件函数内部执行了很长的同步计算，这段函数本身仍然会阻塞主线程。

`requestIdleCallback` 的“空闲时执行”有助于理解调度思路，但不能因此认定 React 的调度器就是调用它。React 有自己的调度实现；`requestAnimationFrame` 也主要用于在绘制前安排动画工作，不等于通用的低优先级任务队列。

## Fiber 与并发特性的关系

Fiber 架构在 React 16 中引入，但“使用了 Fiber”不意味着所有更新都会自动变成可中断更新。

React 18 引入的并发渲染能力，为不同重要程度的更新提供了更直接的使用方式。例如 transition 可以将某些更新标记为非紧急，让紧急交互有机会优先处理。并发渲染是关于工作如何被安排，不意味着多个组件在主线程上同时并行执行。

Suspense 则处理渲染过程中某些内容尚未就绪时的协调与回退界面。它可以与并发渲染协作，但与时间切片不是同一个概念。

## 对业务开发有什么帮助

了解 Fiber 后，更容易理解为什么需要保持渲染纯粹、为什么一次渲染调用不一定对应一次 DOM 提交，也更容易避免把性能问题都归因于 diff。

遇到卡顿时，应先定位主线程时间花在哪里。长列表可能需要虚拟化；重复计算可以考虑缓存；适合独立执行的重计算可以交给 Worker；布局抖动则需要减少不必要的 DOM 测量与修改。调度可以改善响应机会，但不能让昂贵的工作凭空消失。
